# Performance baseline — September 19, 2026

Follow-up: [implemented improvements and validation](2026-09-19-improvements.md).

The largest observed delay is generated note briefings, especially Claude
Quick. Ordinary note navigation is fast in this fixture, and Pilot already
reuses its runtime effectively. Measure and improve the Quick path first.

## Method and limits

macOS arm64, Bun 1.3.9, production Vite UI in headless Chrome, loopback server.
All model requests and note data were synthetic. No personal vault content was
sent to a model. The working dev vault and its provider selections were unchanged.

Pilot uses the production `PilotChats` path, current YAML defaults, and three
fresh-session/follow-up pairs per provider. These are deliberately short,
no-tool replies. They establish overhead, not research-task throughput or a
model-quality comparison. Fresh sessions after the first reuse loaded JS
modules and provider caches. Speculative composer prewarming had no deliberate
head start. Timings end at the server; browser delivery adds polling/rendering.

The note fixture contains 2,000 assertions, 101 entities, one shared source, and
one memory note. Its central entity has all 2,000 assertions and 100 neighbors.
The browser requests the normal one-assertion header response. Model briefing
requests were disabled during browser measurements and measured separately on
10 connected synthetic notes with a roughly 12 KB prompt. These small samples
are not p95 estimates or claims about a large personal vault.

Raw measurements: [baseline.json](2026-09-19-baseline.json).

## Pilot

Medians of three trials, seconds:

| Configuration | Session | Setup to dispatch | First text | Complete |
| --- | --- | ---: | ---: | ---: |
| ChatGPT / Pi, GPT-6 Astra, medium | Fresh | 0.004 | 2.232 | 2.411 |
| ChatGPT / Pi, GPT-6 Astra, medium | Reused | 0.0004 | 2.108 | 2.921 |
| Claude, Opus alias, default effort | Fresh | 0.499 | 1.594 | 2.052 |
| Claude, Opus alias, default effort | Reused | 0.0005 | 1.071 | 1.080 |

The very first Pi setup took 182 ms; later fresh sessions took about 4 ms.
Claude fresh setup ranged 481–917 ms. Reused setup was below 1 ms for both.
No tools ran. Time after dispatch includes provider queueing, network, and
model work; these measurements cannot separate those components. Provider
variation is larger than the remaining reused-session setup overhead.

The UI polls working conversations every 300 ms, so server first-text is not
identical to user-visible first-text. Polling cadence and browser paint should
be measured before claiming a complete end-to-end improvement.

## Notes and Quick

- Initial page to note header after two animation frames: **474 and 537 ms**.
- Subsequent navigation after two animation frames: approximately **24–45 ms**;
  DOM updates were approximately **3–13 ms**. This measures header/readiness,
  not generated summary or relationship descriptions.
- Subsequent note HTTP requests were approximately **4–10 ms**.
- Dense entity and briefing preparation: **238 ms** on first in-process read,
  then **43–47 ms** combined. Briefing input construction accounts for about
  41–44 ms of the warm total, before any model work.
- ChatGPT Quick, GPT-6 Astra / low: summary at **1.54, 1.81, 5.24 s**;
  completed descriptions at **8.11, 8.56, 11.19 s**. All three passed schema
  and evidence validation.
- Claude Quick, Haiku alias / default effort: first run's summary at **31.67 s**,
  complete at **34.25 s**. The second request hit the configured **60 s**
  deadline; the original profiling script stopped before a third request.
  This is a latency/reliability finding, not an estimated median.

Claude's successful Quick result reported 3,589 output tokens versus 222–282
for ChatGPT. Provider accounting and internal rounds differ, so token counts
alone do not establish the cause. The first visible Claude preview is the
StructuredOutput tool's JSON, not arbitrary assistant prose. Investigate
thinking, preliminary answers, schema-generation/repair rounds, and the coding
system-prompt overhead separately. Do not weaken schema/evidence validation to
make a latency number smaller.

## Local overhead worth removing

One idle tab made **20 session requests in 6 seconds**: eight Pilot-list reads
and twelve legacy-history reads. `HomeView.svelte` and `Pilot.svelte` both poll
history, even though it is now read-only. There were also duplicate graph,
note, recent, and session requests during startup. Initial overlapping reads
took around 240 ms on the client, versus single-digit milliseconds during
navigation. That duration includes queueing; it is not an isolated CPU profile
of each handler.

`createNoteBriefingService` constructs the full evidence input before checking
the persisted briefing cache. The warm preparation cost above therefore matters
even on cache hits. Any cheaper invalidation scheme must preserve updates to
source evidence, exclusions, model settings, and date-sensitive unread views.

## Recommended order

1. **Investigate and bound Claude Quick's generation work.** It should not
   spend tens of seconds producing a short summary and ten descriptions.
   Trace phase durations and counts without retaining prompt/response content,
   then test a narrow Quick-specific execution policy against the same corpus.
2. **Consolidate session polling and stop periodically fetching immutable
   history.** One refresh owner and shared in-flight requests would remove
   verified duplication without changing model behavior.
3. **Reduce perceived briefing latency.** Preserve the existing immediate
   connection list and summary preview; investigate progressively displaying
   validated descriptions, and revision-based cache checks before rebuilding
   all evidence.
4. **Profile representative long Pilot tasks.** The runtime-reuse work is
   already effective. Next measure model/tool round count and redundant
   retrieval on longer conversations before changing model defaults.

No production performance behavior or model defaults were changed in this
profiling pass.

## Reproduction

- `bun test/support/profilePilotProviders.ts --live 3`
- `bun test/support/profileNoteBriefing.ts pi gpt-6-astra live 10`
- `bun test/support/profileNoteBriefing.ts claude haiku live 10`
- `bun test/support/profileNoteFixture.ts > /tmp/bb-note-fixture.json`
- Start `web/server.ts` with `BIGBRAIN_VAULT` set to the printed fixture root
  and an unused `BIGBRAIN_WEB_PORT`; do not run a background gardener there.
- Run `test/support/noteLatency.profile.cjs` with `NOTE_PROFILE_FIXTURE` pointing
  to that JSON and `GRAPH_PREVIEW_URL` pointing to the scratch server.
  Set `PLAYWRIGHT_MODULE` if Playwright is installed outside the repo.

`prepare` mode of the Quick benchmark is local-only and is now the default.
Live-mode failures are recorded as measurements; subsequent trials continue.
