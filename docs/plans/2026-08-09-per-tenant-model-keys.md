the shape sketched in #70 where it conflicts (the provisioner cannot mint
keys — see Findings).

## Context

Every tenant's editor runs spend on ONE service-wide `ANTHROPIC_API_KEY`
(secrets.env → warden's scrubbed run env). Acceptable for 2–3 known alphas;
a named deviation in the run-environment contract. The costs: blast radius =
the operator's wallet, all-or-nothing revocation, zero per-tenant attribution
(#40 phasing and #41 billing both need attribution to exist).

## Findings (Admin API, verified against docs 2026-08-09)

- **Workspaces are fully programmatic.** `POST /v1/organizations/workspaces`
  creates; `POST .../workspaces/{id}` renames; `POST .../workspaces/{id}/archive`
  archives — and archive **revokes every key in the workspace**, irreversibly.
  Cap: 100 active workspaces per org. Auth: `x-api-key: <sk-ant-admin…>` +
  `anthropic-version: 2023-06-01`.
- **API keys can NOT be created via the API.** Console-only, by design
  (Admin API FAQ). The API can list keys (`partial_key_hint`, `workspace_id`,
  `status`) and deactivate them.
- **Workspace spend limits are Console-only** too (the spend-limits API is
  Claude-Enterprise-only).
- **Usage/cost reports filter per workspace** (`usage_report/messages?workspace_ids[]`) —
  the free attribution leg of #85.
- **WIF (service accounts + federation)** is the only fully-automatic
  credential path: short-lived tokens minted against an OIDC issuer we would
  run at bigbrain.cool. Real build (issuer, JWKS, org:admin bootstrap,
  per-run token refresh). That is the graduation rung, not this one.

## Decision: a stocked key pool

Since key-minting needs a human in the Console, move the human OFF the signup
path: stock credentials ahead of time, assign automatically.

1. **Stock** — `keys stock <n>` creates n pool workspaces via the Admin API
   (`bb-pool-<hex6>`). Nick opens the Console once per batch: in each pool
   workspace, create one key named `editor` and set the monthly spend limit
   (Console-only). Minutes of work per ~5 tenants.
2. **Intake** — `keys add` reads one pasted key from stdin, matches it to its
   workspace via the Admin API's `partial_key_hint` (`sk-ant-api03-R2D...igAA`
   → prefix/suffix match), encrypts it (AES-256-GCM, master key
   `S_TIER_KEY_MASTER` in secrets.env, generated by bootstrap), and inserts a
   `model_keys` row. The plaintext exists only in the paste moment and in a
   run's child env — never in logs, output, chat, or any vault tree; every
   display shows the hint.
3. **Assign** — the provisioner ensures a key before init (new seam
   `ensureModelKey(tenantId)`): pop the oldest free pool row, rename its
   workspace to the tenant id (best-effort), decrypt for the child env.
   Signup stays self-serve while the pool has stock; `keys status` shows depth.
4. **Run** — the warden resolves the key per tenant (`modelKeyFor(id)`)
   instead of holding one value. A tenant with no key and no fallback: skip
   the spawn, log loudly, NO breaker penalty (operator problem, not tenant's).
5. **Retire** — `keys retire <tenant>` archives the workspace (instant,
   irreversible revocation of its key) and marks the row.

**Fallback + migration:** the shared `ANTHROPIC_API_KEY` becomes a fallback
that logs a deprecation warning per use. `keys migrate` assigns pool keys to
the live alpha tenants and renames their workspaces; once every active tenant
resolves a pool key, the shared key comes out of secrets.env. Config requires
at least one path (`S_TIER_KEY_MASTER` or `ANTHROPIC_API_KEY`) to serve.

## What this does NOT do

- No WIF / service accounts (rung 2 — files as its own issue when signup
  volume makes Console batches annoying). BYOK later rides the same
  `model_keys` slot: a tenant-supplied key is just a row with a different
  provenance.
- No key rotation flow (retire + re-assign covers the emergency; scheduled
  rotation is rung-2 work).
- No tenant-deletion flow — `keys retire` is the credential half; the vault
  half stays manual.
- Spend limits stay Console-set per workspace; our own metering
  (`registry.addUsage`) and the circuit breaker remain the fine-grained
  control.

## Pieces

- `control/keycrypt.ts` — AES-256-GCM `encryptKey`/`decryptKey`,
  `v1:<iv>:<tag>:<ct>` hex format, 32-byte hex master.
- `control/adminApi.ts` — thin fetch client (seam-injected for tests):
  createWorkspace, renameWorkspace, archiveWorkspace, listApiKeys,
  deactivateApiKey, `matchKeyToHint`.
- `registry.model_keys` — `key_id PK, workspace_id, tenant_id NULL,
  api_key_enc, key_hint, status('pool'|'assigned'|'retired'), created_at,
  assigned_at`. Assignment is a transaction (two concurrent signups never get
  the same key).
- `control/modelKeys.ts` — `makeModelKeyResolver(registry, master, shared)`
  used by both the control server (provision + token mints) and the warden
  entrypoint.
- `control/keys.ts` — the operator CLI (stock/add/status/migrate/retire).
  Parses secrets.env in code; runs over plain ssh as the bigbrain user (no
  systemd, no keychain).
- `bootstrap.sh` — generates `S_TIER_KEY_MASTER` if absent (like
  BETTER_AUTH_SECRET); secrets template mentions `ANTHROPIC_ADMIN_KEY`.

## Operator secrets (never in chat, never in git)

- `ANTHROPIC_ADMIN_KEY` — Console → Settings → Admin keys; pasted into
  `/srv/bigbrain/.config/s-tier/secrets.env` via `ssh -t … cat >>` (stdin,
  no history). Control server reads it for workspace ops; keys CLI reads it
  for stock/add/migrate/retire.
- `S_TIER_KEY_MASTER` — box-generated, never leaves the box.
