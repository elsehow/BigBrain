# Portals

2026-10-15. Decided in conversation. Replaces the lens/server split in
`lenses-and-servers.md`, and §1 and §3 of `2026-10-13-lenses-are-the-door.md`.
§2 of that plan, the door, stands.

## The sentence

> A Portal is a rule over your vault that other people can connect to.
> Everyone connected brings a rule of their own, and what their rules let
> through comes out of the Portal on your Field.

## Why

A lens and a server are two names for one thing. Migration 5
(`lib/lensMigrate.ts`) turned each server's rule into a lens named after
the server, so a migrated vault shows every server twice, once as each.
`Lens.servers` allows one lens on several servers, but the migration made
every lens one server's.

One noun also covers the agent grant (#303). Connecting someone to a Portal
works the same way for a person and for an agent.

## The model

- **A Portal is yours.** It is a lens: `lenses/<id>.json`, its members a
  view over inclusion assertions (`lib/lenses.ts`, `lib/views/lens.ts`).
  None of that changes.
- **With nobody connected, a Portal is private** and needs no server. That
  is today's unshared lens.
- **Connecting someone puts the Portal on a server.** Each person has one
  rule per Portal, and each Portal is on at most one server. To use a rule
  in two Portals, copy it.
- **Each member brings their own rule, or none** (read only). Members never
  see each other's rules (unchanged).
- **Not everything coming out of a Portal came from someone's vault.** A
  member can contribute to a server directly (`POST /v1/evidence`), not only
  through a lens. Label outside items by member ("from Ada"), not by vault.
- **The code keeps its names.** The log stores inclusion verdicts under
  `lens_…` ids and can't be renamed, so "Portal" is the word on screen and
  the code keeps `lens`, `server` and `connection`, the same way Desktops
  are pilots in the code. `lenses/<id>.json` keeps its `servers` array, and
  the app writes at most one entry. No vault changes shape
  (design-principles §5).

## Servers

People self-host servers. BigBrain runs none (CLAUDE.md, "There are no
hosts"). A server is `bin/shared.ts serve` on a machine someone in the
Portal runs (`deploy/shared-vault/README.md`). This is not federation:
each Portal lives on one server, and every member's app talks to it
directly.

- **One server holds several Portals.** Today a server is one vault, named
  by `--vault`. It becomes a directory of Portal vaults, and the routes name
  the Portal. Members and credentials belong to a Portal: being a member of
  one Portal on a server says nothing about the others. A server holding one
  vault keeps answering at today's routes.
- **Portals are created from the app.** Today the operator runs
  `bigbrain shared init` on the server. Instead, the app holds a credential
  for the server itself, separate from any Portal's members, that lets it
  create Portals there. See P4.
- **A Portal is connected to a server from the app.** On a Portal, "Invite
  someone" asks which server to put it on. Settings lists the servers you
  have added as places Portals can live. "Server" stays a settings word; the
  Field and the gear don't show servers.
- **Joining** follows `lenses-and-servers.md` Phase 2. The invite link names
  the server and the Portal.
- **Moving a Portal to another server** means copying its logs and pointing
  members at the new address. This comes later, but nothing here should rule
  it out.

## Signed events

Today the server vouches for authorship: `lib/sharedMembers.ts` says the
holder of a live credential for `alice` submitted this event, and notes that
portable signatures are deferred. Now they aren't. Every event written to a
Portal is signed with a key the member holds. The server checks the
signature against the Portal's membership instead of vouching for the
author itself, so any copy of an event can be checked no matter where it
came from.

- **The member stays the identity.** That is the handle: immutable and never
  reused (`docs/shared-vault.md`). Keys replace bearer credentials as the
  proof that a member wrote something.
- **One key for each device and each agent,** each bound to its member in
  the Portal's membership. `author.kind` follows from which key signed, so
  person versus agent is still never read from the payload
  (design-principles §2, `lib/voice.ts`).
- **A member's keys are good in one Portal only.** Nothing links your
  memberships in two Portals. An identity that spans Portals is not part of
  this plan.
- **Membership is a signed log in the Portal.** The owner adds and removes
  members and their keys. If a member loses a key, the owner binds a new
  one, the way they mint a new credential today. Events signed before that
  stay valid.
- **Keys live in `~/.config/bigbrain/`** next to the connections
  (`lib/sharedConnections.ts`), never in a vault: a vault is a git repo of
  content.
- **Events already on a server stay readable,** shown as vouched for by
  that server.
- **Reads keep bearer credentials,** the Claude connector included. Only
  writes are signed.
- **Call them member keys in the code.** "Identity" already means something
  else here: `lib/sharedIdentityLog.ts` records which landings are one work.

This raises `SHARED_PROTOCOL` (`lib/sharedProtocol.ts`). It ships in the
same change as several Portals per server, since both change the API
between the app and the server.

## Peer-to-peer later

Signed events turn peer-to-peer sync into an added transport, not a
redesign: a server becomes a peer that is always on. That is #318 and is
not part of this plan.

## On the Field

- A Portal draws as a cube: today's lens cube (#301, #317). Your items in it
  sit around it, and items from other members come out of it. Server items
  are already placed beside whatever they link to (`seatLayout`,
  `lib/views/layout.ts`).
- Clicking a cube filters the Field to the Portal (#301). That replaces
  picking a server in the gear's list.

## Decide

- **P1. What Off means.** Proposal: Off stops both directions. Your items
  are withdrawn (`lib/lensSync.ts` already withdraws and restores them) and
  other members' items stop showing on your Field, while your rule and your
  membership are kept. Leaving a Portal is a separate action.
- **P2. How outside items are marked.** `--activity` is the theme's only
  accent, and it already means live or needs attention: selection, focus, a
  working lens, due items, errors, search hits. Proposal: outside items get
  a quieter mark of their own, and `--activity` marks only what has come out
  of a Portal since you last looked.
- **P3. A lens that already lists two servers.** Proposal: show it as a
  Portal on each server, and offer to split it into one lens per server. The
  owner does the split; nothing is migrated.
- **P4. Who may create Portals on a server.** Proposal: the server's
  operator, and anyone the operator gives a creator credential.
- **P5. The gear's list.** Once servers become Portals on the Field, the
  list holds only Personal. Decide whether it stays.

## Order

1. **The word.** "Portal" on screen in settings, the Field and the lens
   panel, with servers described in settings as places Portals can live. No
   data change.
2. **The server.** Several Portals per server, creating a Portal from the
   app, connecting a Portal to a server, and signed events, all in one
   protocol change.
3. **The Field.** Marks and Off, once P1 and P2 are decided.
4. **The grant.** #303 becomes connecting an agent to a Portal.
